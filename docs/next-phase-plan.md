## 2. 推荐下一阶段：Phase 7「安全与身份」

> 本轮实际范围：7.2 双人资料 + 7.4 原生能力基线。  
> 7.1 应用锁、7.3 隐私中心暂缓；等后续确认后再做。

这一阶段先补私密性和个性化，并为后续功能一次性准备原生能力，减少反复安装 APK。

### 7.1 应用锁与隐私保护（P0）

功能：

- 打开 App 或从后台返回时，需要生物识别或 6 位 PIN
- 后台超过可配置时间自动锁定
- 锁定页只显示品牌与解锁入口，不显示任何私密数据
- Android 截图与最近任务预览屏蔽
- PIN 使用加盐哈希后存入 SecureStore
- 连续输错锁定冷却
- 忘记 PIN 时：退出登录并使用 Supabase 账号重新登录后重置本地 PIN

技术：

- `expo-local-authentication`：指纹/面容
- `expo-screen-capture`：Android `FLAG_SECURE`
- `expo-secure-store`：保存 PIN 哈希与锁设置
- `expo-crypto`：哈希
- 新增本地 LockProvider，包在导航外层
- 不做端到端加密；这是界面与设备级保护

验收：

- 冷启动、后台返回都要求解锁
- 生物识别失败可回退 PIN
- 截图被阻止，最近任务不显示内容
- 忘记 PIN 可重新登录恢复
- 两个账号各自设备上的 PIN 独立

风险：

- 忘记 PIN 必须有明确恢复路径
- 截图屏蔽会影响用户主动截图，可提供开关但不建议默认关闭
- SecureStore 在某些 Android 机型上可能被清除，需要可重建

### 7.2 双人资料与昵称头像（P0）

功能：

- 两位用户分别设置昵称、头像
- 首页问候语使用昵称
- 纸条、动态作者显示昵称，而不是「我 / TA」
- 头像进入现有压缩、私有上传链路
- 可修改昵称与头像

数据：

新增 `profiles` 表：

- `user_id uuid primary key`
- `display_name text`
- `avatar_path text`
- `created_at` / `updated_at`
- RLS：两位成员可读；只能插入/更新自己的行
- 头像仍存 `photos` 私有桶，路径 `auth.uid()/profile/...`
- 头像 signed URL 复用现有批量生成逻辑

验收：

- A、B 各自改名和头像，对方可见
- 资料修改后所有作者标签更新
- 第三账号读不到 profiles
- 头像大小仍符合压缩规范

### 7.3 隐私中心（P0）

功能：

- 查看当前账号与设备
- 退出当前账号 / 退出所有设备
- 清除本机缓存与已下载图片
- 查看隐私说明：数据只存在你们的 Supabase 项目与私有 Storage
- 应用锁设置入口

技术：

- Supabase `signOut({ scope: 'global' })`
- React Query 缓存清理
- expo-image 磁盘缓存清理
- 不删除云端数据

### 7.4 原生能力基线（建议一起安装）

为了后续 Phase 8/9 尽量走 JS 热更新，建议在 Phase 7 的 APK 中一起安装：

- expo-local-authentication
- expo-screen-capture
- expo-secure-store
- expo-crypto
- expo-notifications（先不请求权限，不发通知）
- expo-sharing（先不导出）
- expo-haptics

这样 Phase 8 的搜索/回顾/导出、Phase 9 的提醒可以只发布 JS 更新；只有真正需要新原生能力时才再次构建 APK。

版本策略：

- 新原生版本：`1.2.0`，`versionCode 4`
- 构建后安装新 APK
- 后续 JS 更新全部使用 runtime `1.2.0`

## 3. 后续阶段路线

### Phase 8「查找、回顾与导出」（P1）

> 现状：8A 全局搜索、照片说明/收藏已完成；8B-1 年度回顾与 JSON 导出已完成。  
> 8B-2 照片 ZIP、文件夹和加密压缩包尚未实现。

- 全局搜索：纸条、照片说明、美食、计划、纪念日
- 中文搜索使用 `pg_trgm` 与相关索引
- 照片说明编辑、照片收藏
- 年度回顾：照片拼贴、记录数量、常去城市、收藏美食
- 导出：
  - 数据 JSON
  - 照片 ZIP 或文件夹
  - 可选加密压缩包
  - 通过系统分享发送到自己的备份位置
- 验收：搜索结果准确；导出可打开；大相册导出不会 OOM

### Phase 9「提醒与通知」（P1）

- 纪念日提前提醒、当天提醒
- 待办到期提醒
- 每天/每周可选写日记提醒
- 通知设置与静音时段
- 先做本地通知；跨设备推送后续可加 Supabase Edge Function

### Phase 10「内容与互动增强」（P2）

- 相册封面、照片说明、收藏、批量移动/删除
- 小窝统一动态流：照片 + 纸条 + 美食 + 完成计划
- 对照片/纸条/美食做轻量回应（爱心等）
- 美食评分、标签、收藏视图、月/年统计
- 计划负责人、优先级、重复任务
- 数据表增量字段、reactions 表、RLS 与索引

### Phase 11「离线与可靠性」（P2）

- React Query 持久化到本地
- 弱网下查看已缓存数据
- 纸条/计划/美食的离线写入队列
- 冲突提示与手动重试
- signed URL 过期自动续签
- Storage 孤儿文件清理、缩略图一致性检查

## 4. 暂不纳入

- 端到端加密：会改变上传、缩略图、signed URL 和密钥管理，需要单独架构阶段
- 聊天/公开分享/多人协作：与「仅供两个人」的定位冲突
- AI 自动分析纪念内容：会扩大隐私面
- 桌面组件：原生成本高，等核心隐私与备份完成后再评估

## 5. 需要确认的产品决策

1. 应用锁：生物识别 + PIN 是否可接受？自动锁定时间默认多少？
2. 截图屏蔽是否默认开启？是否需要给用户开关？
3. 双人资料是否需要头像，还是只做昵称？
4. 提醒先做本地通知，还是直接做跨设备推送？
5. 导出是否需要加密，还是先做普通 ZIP？
6. Phase 7 是否按建议一次性加入原生能力基线？

## 6. 交付节奏

每个 Phase 仍按当前流程执行：

1. 先说明方案、数据迁移和 UI
2. 给出完整代码
3. 运行 `tsc`、`lint`、Android bundle
4. 说明 APK 构建或 OTA 发布方式
5. 真机验收，确认后进入下一阶段

Phase 7 因包含原生模块，必须构建并安装一次新 APK；之后优先通过 EAS Update 发布 JS。
